# MPM

MPM (Managed Persistent Memory) is an observable substrate for long-lived
autonomous systems. It preserves what an agent knows, what it is trying to
accomplish, why it made a decision, and what actually happened across sessions.

> **Technical specification:** See [docs/SPEC.md](docs/SPEC.md) for MPM's
> architecture, behavioural contracts, cognitive model, runtime semantics,
> reliability guarantees, and implementation reference.
>
> **The idea behind it:** See
> [docs/PRINCIPLE-OF-INHERITED-INTELLIGENCE.md](docs/PRINCIPLE-OF-INHERITED-INTELLIGENCE.md)
> — why MPM is built around an accumulating body of knowledge rather than
> around individual agents.

## Why MPM?

An agent can remember a conclusion and still lose the reasoning that produced
it. MPM gives memories, decisions, theories, evidence, work, lessons, and skills
distinct lifecycles so future sessions can continue an investigation instead of
starting over.

- **Reasoning with history:** decisions retain their rationale; theories carry
  validation criteria; evidence can support or challenge a belief.
- **Continuity across sessions:** wake context surfaces relevant durable state,
  open work, and the previous handoff. Work completion and session closure are
  separate events.
- **Traceable changes:** provenance and activity records make it possible to
  inspect who produced an artifact and what changed. Invalidated foundations
  surface dependent decisions and theories for re-evaluation.
- **Local persistence:** one SQLite database with FTS5 holds the cognitive
  substrate. Semantic recall can use a local Ollama embedding provider; no
  separate vector database or remote storage service is required.
- **Shared agent access:** the operator CLI, JSON tool calls, and stdio MCP
  server use the same substrate and tool registry.

MPM is a persistence and reasoning layer. Agent runtimes and orchestration
systems integrate with it to retain intellectual progress.

## Agent integration: the managed behavioural block

**MPM requires a managed behavioural block in the host's persistent agent
instructions for reliable MPM use.** This is a required part of a functional
host integration, not an optional extra.

Concretely: a host may technically expose the MPM tools while still failing to
use MPM reliably if the managed behavioural block is absent. Tools being
visible is not the same as the agent knowing when and why to reach for them.

The instructions that make MPM usable are split deliberately:

| Layer | Answers | Where |
|---|---|---|
| Managed behavioural block | **When and why** the agent should use MPM | Host's persistent agent instructions |
| Tool descriptions, schemas, discovery surfaces | **How** to use MPM | MPM's own tool registry |
| [Agent protocol](agent_installation/mpm-agent-protocol.md) | Detailed semantics | Repository documentation |

For **OpenCode** — the officially supported agent host for this release —
the integration is layered:

```text
AGENTS.md managed block         -> persistent behavioural bootstrap
mpm-opencode plugin             -> dynamic wake / context injection
```

Dynamic injection **supplements** the persistent managed block. It does not
replace it: wake context supplies current durable state, and the managed block
is what tells the agent how to behave with MPM across the session.

The approved managed block is shown below. It is host-neutral — bare canonical
tool names, no host-specific prefix. OpenCode is the only supported host in
this release, and it renders this block unmodified from the canonical source in

# MPM — durable knowledge for every agent

**Reusable knowledge belongs in shared MPM records** — any agent can retrieve
them without knowing which session found them. **A handoff carries execution
state, not knowledge**: it references those records. Your session ends; your
knowledge need not. **Do not make your successors rediscover what you already
learned.**

| Situation | Record |
|---|---|
| Reusable fact, constraint, root cause | `mpm_memory` action `save` |
| Choice and rationale | `mpm_decisions` action `record` |
| Insight, warning, or practice worth repeating | `mpm_lessons` action `propose` — a proposal, pending operator review |
| Supporting or contradicting observation | `mpm_evidence` action `add` |
| Unverified hypothesis — never a fact or lesson | `mpm_theories` action `propose` |
| Objective spanning sessions | `mpm_work` action `create` — reach it with `mpm call` |
| Procedure that has proved itself | `mpm_skills` action `save` |
| External document to ingest for later consultation | `mpm_references` action `add` |
| Unfinished work or session transition | `mpm_handoff` action `write` |
| Routine or transient information | nothing |

**Persist as soon as it becomes useful**, not at session end — you need not
predict your session ending.

**Handoff** — a title is not continuation state. `summary` for what was
completed; `commitments` for unfinished work, next actions and
files/branches/PRs; `open_questions` for blockers; shared-record ids
alongside — reference records, don't copy them. Write one for a transfer, a
finished substantial task, or before you stop; not for an acknowledgement, not
after every tool call. **No signal reliably marks a session end**: turn
completion, idle, archive and shutdown are not one.

**When your work changes what is known**, supersede or flag the affected
record and say why; do not rewrite history.

Wake context arrives at session start (recover it through `mpm_context` using
`read_wake_context` if not); follow its pointers — they point into durable
knowledge, not a complete or unquestionable account, and stored state may be
outdated or superseded. Discover unfamiliar operations with `mpm_help` action
`show` — `mpm_help` and `mpm_work` are reached with `mpm call <tool>`, not as
native tools on this host; the same path reaches whatever else it does not
expose.
References are a distinct corpus, not memories: read the underlying source rather than relying solely on a search-result summary.
Check its version and freshness. Full contract:
`~/.mpm/agent_installation/mpm-agent-protocol.md`.

## How it fits

```text
Operators                     Agent hosts
    │                         │         │
    ▼                         ▼         ▼
mpm CLI                  mpm call    mpm-mcp (stdio)
    └─────────────────────────┴─────────┘
                              │
                    Shared core and tools
                              │
                      SQLite substrate
                              ▲
                   Scheduler and critic
```

Five binaries ship together: `mpm`, `mpm-mcp`, `mpm-scheduler`, `mpm-critic`,
and `mpm-telemetry`. The telemetry sidecar records LLM invocation economics in
its own `telemetry.db`, separate from the cognitive substrate.

## Try it

MPM installs to `~/.mpm`, which is both the Git checkout and the runtime
root — one directory holds the source, the compiled binaries, and your data.

`install.sh --bundle` can separate the two: the runtime becomes a versioned
bundle under `~/.mpm/releases/<rev>` and `~/.mpm/current` points at the active
one, while the data root stays exactly where it is. That layout is opt-in, and
converting an existing installation to it is a separate, authorised
migration — see
[§1g of the runtime installation reference](docs/INSTALL.md#1g-the-versioned-runtime-bundle-layout-opt-in).

Building requires Go 1.26.6 or newer, Make, and a C toolchain for SQLite/CGO.
The Makefile supplies the required FTS5 build flags.

```bash
git clone https://github.com/flowbyte-com/mpm ~/src/mpm
cd ~/src/mpm
make build          # developer artifacts -> ./.build/bin/ (disposable)
./.build/bin/mpm --help
```

`make build` writes `.build/bin/` and nothing else. The binaries the
services actually execute live in `~/.mpm/bin/`; only `make install`
(or `./install.sh`) puts them there. Building can no longer overwrite a
running installation.

For the full user-space install on Linux with systemd:

```bash
./install.sh
mpm ops init directives
mpm doctor
```

That is the whole install. `install.sh` builds the five binaries into
`~/.mpm/bin/` and links only `mpm` and `mpm-mcp` into `~/.local/bin` for your
PATH; there is no wrapper and no `mpm.real`. The three daemon binaries
(`mpm-scheduler`, `mpm-critic`, `mpm-telemetry`) are invoked from
`~/.mpm/bin/` by systemd and are not on your PATH.

**Advanced:** `install.sh` also supports running from an alternate checkout
(e.g. `~/projects/mpm`) while still installing binaries and runtime state
under `~/.mpm`. That is supported but not the primary layout.

Follow [Agent Integration Installation](agent_installation/INSTALL.md) for
prerequisites, host setup, verification, updates, and recovery. It is the
installation and integration authority for supported agent hosts. The
[MPM runtime installation reference](docs/INSTALL.md) covers runtime-specific
configuration and services.

Once installed, inspect the substrate and restore session context:

```bash
mpm status
mpm wake --compact
```

The [specification's Quick Start](docs/SPEC.md#5-quick-start) contains the
CLI-only path, manual service setup, and first cognitive commands.
