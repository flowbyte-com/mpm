## 0. Executive summary

The managed instruction block that OpenCode loads on every turn was **11,225
bytes / 2,009 tokens** of prose. It is replaced here by a **2,561-byte /
593-token behaviour matrix** — a **70.5% token reduction** — that carries the
operational core of the contract and points at the canonical protocol for the
elaboration.

| | Old (contract 3.0.0) | New (contract 4.0.0) | Δ |
|---|---|---|---|
| bytes | 11,225 | 2,561 | **−77.2%** |
| words | 1,564 | 376 | −76.0% |
| tokens (`cl100k_base`) | 2,009 | **593** | **−70.5%** |
| tokens (`o200k_base`) | 2,002 | 596 | −70.2% |

**How the bytes are counted**, because a reviewer will count differently
and get a different number. 2,561 is the **renderer's output**: the block
from `<!-- BEGIN MPM MANAGED BLOCK -->` through the newline that follows
`<!-- END MPM MANAGED BLOCK -->`. The block region *alone* — BEGIN through
the END marker, exclusive of that trailing newline — is **2,560** bytes. The
token figures are unaffected: the trailing newline is inside the measured
string either way. Both numbers are given here because an independent audit
of this branch reported the 2,560 figure (§10.4), and a reviewer comparing
against it should not have to guess which convention was used.

The old block was a **good contract and a bad always-on surface**: it was
paid for on every turn, by every agent, forever, and it spent most of that
budget restating principles rather than telling the agent what to *do*.

Three findings from the audit shaped the design:

| # | Finding | Consequence |
|---|---|---|
| **F1** | **`mpm_handoff write` silently drops every field outside its schema.** `context`, `next_steps`, `artifacts` and `tags` are accepted and discarded; only `summary`, `session_id`, `state`, `commitments` and `open_questions` persist. | The block names the five fields explicitly. An agent that guesses `next_steps` produces a handoff with no next action in it, and nothing warns it. |
| **F2** | **OpenCode v2.1.4 exposes no session-terminal signal.** `session.execution.succeeded` is a *turn* boundary; there is no `session.idle`; `location.shutdown` and the plugin cleanup callback carry no session id; a SIGKILL publishes nothing. | The block triggers handoffs on **agent-judged** grounds and explicitly refuses to read a turn, an idle, an archive or a shutdown as a session end. No automatic terminal handoff is introduced. |
| **F3** | **The substrate's shared collections really are shared.** FTS search does not filter by session: a fact written in session A is retrieved by session B, with no handoff involved. | The block's central instruction — *reusable knowledge belongs in shared records* — is true of the substrate, not aspirational. Verified against the real binary (§7). |

**Recommendation: include in the release candidate**, with the limitations in
§10 read first. The two prior-session deliverables remain open and are not
touched by this branch: PR #148 (`fe767f2`) and PR #149 (`89afaed`).

**Confirmed empirically:** the live file's managed region is byte-identical to
the canonical render, apart from one inserted provenance comment
(`<!-- mpm-provenance: version=… commit=… protocol=… applied=… -->`).

### 1.2 Is the block actually reaching the agent?

Yes. Verified two ways:

1. **Statically** — the AGENTS.md content, HTML comments included, is present
   verbatim in this session's system prompt.
2. **Dynamically** — a project-scope `AGENTS.md` containing a probe marker was
   placed in a working directory and the real host was asked for the marker; it
   echoed it exactly. `opencode debug paths` confirms `$XDG_CONFIG_HOME/opencode`
   is the user-scope root, so `~/.config/opencode/AGENTS.md` is the
   user-scope delivery path.

**The plugin's own hook is a separate mechanism.** `mpm-opencode` injects the
wake context automatically via `experimental.chat.system.transform`. That is
*content* injection; the managed block is *instruction* delivery. They are
complementary and neither substitutes for the other — which is why the block
still teaches the `read_wake_context` recovery path for hosts where the hook
does not fire.

### 1.3 What the old block taught, and what was wrong with it

The 3.0.0 block was ten prose responsibilities ("Inherit before you begin",
"Preserve discoveries as they happen", …) plus a closing principle. The audit
found five distinct problems.

| # | Problem | Evidence |
|---|---|---|
| **A1** | **Verbosity.** 2,009 tokens for ten responsibilities is ~200 tokens each. Most of that is restatement: "The same principle applies to agents", "What you discover can, in turn, become the foundation for another agent's work", "Your session is temporary. What you learn does not have to be." Three paragraphs establish the same premise. | Direct measurement. |
| **A2** | **The budget policy actively forbade compression.** The canonical source said the limits were "14,000 bytes and 2,000 words", that they are "maintainability warnings and review triggers, not budgets to optimise against", and — explicitly — that the 3.0.0 block's size was set to match "because the contract is deliberately behavioural rather than enumerative, and compressing it back toward the old ceiling would undo the approved wording." | `git show f19fb24` — the contract was adopted at 11,224 bytes and the ceiling was raised to match it. |
| **A3** | **No destination vocabulary.** The block named one tool (`mpm_context` / `read_wake_context`) and left every other destination to `mpm_help`. The agent's most expensive mistake on this substrate is writing the **wrong kind of artifact** — a fact where a decision belonged, a theory where a lesson belonged — and the block gave no way to avoid it. | Block content; `internal/core/tools/registry_list.go`. |
| **A4** | **Handoff instructions were scattered and partly obsolete.** "Do not allow a session ending, context compaction or interrupted task to erase knowledge" implied a session-end signal that OpenCode does not provide. The protocol's §4 listed "User goes silent after a substantial exchange" as a session-closing trigger — an inference from silence, not an event. | Protocol §4; F2 above. |
| **A5** | **The knowledge/continuity distinction was not drawn.** Nothing in the old block said that a handoff is *state* and that reusable knowledge belongs in the *shared* collections. An agent optimising for "write a handoff" produces a per-session silo: a discovery that only the session that made it can find. | Block content; the substrate property that makes this matter is §7 Scenario A. |

### 1.4 Source conflicts found

| Conflict | Resolution |
|---|---|
| The canonical source's header said the managed block is "deliberately behavioural rather than enumerative" and names only `mpm_context`; the tool-reference table further down the same file enumerates every tool's actions. | The header now says the block is a **behaviour matrix** that names nine write destinations and defers the per-tool catalogue to the table below it. One file, one story. |
| The header described the "default MCP surface" as three tools; OpenCode's plugin registers **17** typed tools and is not bound by the compact `mpm-mcp` surface at all. | The header now says so explicitly, and says that `MPM_EXPOSE_ALL_TOOLS` is irrelevant to OpenCode. |
| The header said "all five adapters" / "the four copy/paste examples" after four hosts were retired on 2026-10-27. | Corrected to one adapter / one copy-paste example. |
| The protocol taught `mpm_context` action `write_handoff`, which is **not** in the registered `mpm_context` action enum — it exists only on the compact MCP wrapper. | Left as-is and verified: protocol lines 321, 343 and 417 all qualify it as *the compact MCP surface*. The registry's enum does not include it (probed: `unknown action "write_handoff"`). The new block names `mpm_handoff` action `write`, which is in the registry and is a native OpenCode tool. |

### 1.5 User-content preservation

Preserved, and now **tested** rather than assumed. The installer rewrites only
the text between the outer markers; everything above and below survives
byte-for-byte. §8 measures this across four install paths.

### 1.6 Tool discoverability

The block names `mpm_help` action `show` for unfamiliar operations and the
`mpm call <tool>` CLI fallback for what the host does not expose. That last
clause is load-bearing on OpenCode: `mpm_work` is **not** a native OpenCode
tool — it is a registry tool reachable only through the CLI fallback. The
matrix names `mpm_work` action `create` because that is the correct
destination; the CLI clause is what makes the name actionable on this host.

## 2. The proposed block

The host-neutral canonical block, as it now stands in
`agent_installation/MPM_AGENT_INTEGRATION_SNIPPETS.md`:

```markdown
<!-- BEGIN MPM MANAGED BLOCK -->
<!-- source: agent_installation/MPM_AGENT_INTEGRATION_SNIPPETS.md -->

# MPM — durable knowledge for every agent

**Reusable knowledge belongs in shared MPM records** — any agent can retrieve
them without knowing which session found them. **A handoff carries execution
state, not knowledge**: it references those records. Your session ends; your
knowledge need not. **Do not make your successors rediscover what you already
learned.**

| Situation | Record |
|---|---|
| Reusable fact, constraint, root cause | `mpm_memory` action `save` |
| Choice and rationale | `mpm_decisions` action `record` |
| Insight, warning, or practice worth repeating | `mpm_lessons` action `save` |
| Supporting or contradicting observation | `mpm_evidence` action `add` |
| Unverified hypothesis — never a fact or lesson | `mpm_theories` action `propose` |
| Objective spanning sessions | `mpm_work` action `create` |
| Procedure that has proved itself | `mpm_skills` action `save` |
| External document to ingest for later consultation | `mpm_references` action `add` |
| Unfinished work or session transition | `mpm_handoff` action `write` |
| Routine or transient information | nothing |

**Persist as soon as it becomes useful**, not at session end — you need not
predict your session ending.

**Handoff** — a title is not continuation state. `summary` for what was
completed; `commitments` for unfinished work, next actions and
files/branches/PRs; `open_questions` for blockers; shared-record ids
alongside — reference records, don't copy them. Write one for a transfer, a
finished substantial task, or before you stop; not for an acknowledgement, not
after every tool call. **No signal reliably marks a session end**: turn
completion, idle, archive and shutdown are not one.

**When your work changes what is known**, supersede or flag the affected
record and say why; do not rewrite history.

Wake context arrives at session start (recover it through `mpm_context` using
`read_wake_context` if not); follow its pointers — they point into durable
knowledge, not a complete or unquestionable account, and stored state may be
outdated or superseded. Discover unfamiliar operations with `mpm_help` action
`show`; `mpm call <tool>` reaches what the host does not expose.
References are a distinct corpus, not memories: read the underlying source rather than relying solely on a search-result summary.
Check its version and freshness. Full contract:
`~/.mpm/agent_installation/mpm-agent-protocol.md`.
<!-- END MPM MANAGED BLOCK -->
```

### 2.1 On the 200–300 token aspiration

**It is not reachable, and the reason is worth stating plainly.** A 200–300
token block cannot carry: ten write destinations with their actions, the
persistence trigger, the uncertainty rule, the handoff field names, the
handoff trigger set, the no-session-end rule, the maintenance rule, the
wake/recovery path, the discovery path, the reference-discovery commitment and
the shared-records principle. Each of those is an incident-backed commitment
that a test in this repository pins.

What *is* reachable, and what was measured:

| Variant | Tokens | What it drops |
|---|---|---|
| 3.0.0 (today) | 2,009 | — |
| **4.0.0 (this branch)** | **593** | nothing that is pinned |
| A 300-token cut | ~300 | the matrix's `mpm_work`/`mpm_skills`/`mpm_references` rows, the reference-discovery commitment, the maintenance rule and the pointer-semantics clause |
| A 200-token cut | ~200 | all of the above, plus the handoff field names and the no-session-end rule |

The last two are **not offered as options**: they are what the target number
would cost. The 593-token block is the smallest version that keeps every
commitment a test pins. The honest statement is *"593 tokens, not 300"*, with
the delta explained, rather than a number that meets a target by dropping
behaviour.

### 2.2 The layering

The reference stack is now explicitly three-layered, and the boundary is drawn
by one question: **would an agent that never opens the deeper layer get the
behaviour wrong?**

| Layer | Content | Cost |
|---|---|---|
| **the managed block** (always on) | behaviour matrix, persistence trigger, uncertainty rule, handoff contract, wake/recovery path, discovery path | paid every turn, by every agent |
| **the canonical protocol** (on demand) | the full behavioural contract — now a new **THE BEHAVIOURAL COMMITMENTS** section, C1–C12 — plus maintenance semantics, recovery procedures, freshness rules | paid when the agent reads it |
| **the tool-reference stability contract** (in the canonical source) | per-tool action enums and required params | paid when the agent reads it |

The protocol gained a **"THE BEHAVIOURAL COMMITMENTS"** section (C1–C12) that
states all twelve commitments in one place, each cross-referenced to the
section that elaborates it. This is what makes the block's compression safe:
the contract did not shrink, it **moved**, and the moved part is one path away.

### 2.3 Contract version

`<!-- mpm_agent_integration_version: 3.0.0 -->` → **`4.0.0`**.

This is a **major** bump, on the same criterion the 3.0.0 bump used: the
rendered block an adapter installs is a *different document*, so every adapter
must be re-verified against the new contract. Two changes coincide — the
always-on text is a different document, and the block now enumerates write
destinations. The MPM **product** version did not move: this marker versions
the behavioural contract, not the software.

## 3. The behaviour matrix, and why each row exists

| Situation | Destination | Why this row exists |
|---|---|---|
| Reusable fact, constraint, root cause | `mpm_memory` action `save` | The default destination for a discovered fact. "Constraint" and "root cause" name the two highest-value discoveries an agent makes. |
| Choice and rationale | `mpm_decisions` action `record` | A decision is not a fact; storing it as a memory loses the reasoning, which is the entire value of the record. |
| Insight, warning, or practice worth repeating | `mpm_lessons` action `save` | A lesson is a *reusable correction or practice* — what to do differently, or what proved worth doing. The registry's `mpm_lessons save` takes `fact` + `type`, and the type vocabulary is exactly **`insight`, `warning`, `practice`** (`internal/core/tools/registry_list.go`). The row uses those three words verbatim so an agent cannot map the situation onto a type that does not exist — a live call with `type: "correction"` is refused with `invalid lesson type "correction": must be one of warning, practice, or insight`. |
| Supporting or contradicting observation | `mpm_evidence` action `add` | Evidence attaches to an existing artifact and carries weight. It is never a destination on its own — it always points at a record. |
| Unverified hypothesis — never a fact or lesson | `mpm_theories` action `propose` | The uncertainty rule, encoded as a *destination*. A hypothesis that has not been tested is stored `pending` and is not retrievable as a memory. |
| Objective spanning sessions | `mpm_work` action `create` | Durable work state is a distinct artifact from a memory: it has a lifecycle (`open`/`done`/`cancelled`) and an event ledger. |
| Procedure that has proved itself | `mpm_skills` action `save` | A validated, repeatable procedure — different from a lesson (which is a correction) and from a memory (which is a fact). |
| External document to ingest for later consultation | `mpm_references` action `add` | References are a **distinct corpus**, not memories. The row exists because an agent that treats them as memories concludes the corpus is empty when a memory search returns nothing — the exact inference that caused the 2026-09-04 incident. The wording says *ingest* because `add` really ingests: it fetches a URL or parses a local file into chunks (see D6). |
| Unfinished work or session transition | `mpm_handoff` action `write` | Execution state, not knowledge. The row is placed last so the matrix's order reads as "knowledge first, state last". |
| Routine or transient information | **nothing** | The negative control. Without this row the matrix reads as "always persist something", which is the opposite of the contract's "value knowledge, not volume" commitment. |

### 3.1 The triggering rationale

**Persistence trigger.** "Persist as soon as it becomes useful, not at session
end — you need not predict your session ending." The clause after the dash is
load-bearing: it removes the excuse that agents use to defer persistence
("I'll write it up when I wrap up"). The persistence trigger is *usefulness*,
not *completion*.

**Handoff trigger.** Agent-judged, on **three** grounds — a **transfer**, a
**finished substantial task**, and **before you stop** — with two explicit
exclusions: **not** for an acknowledgement, and **not** after every tool call.
The old block's failure mode was the opposite one (deferring everything to
session end, which then never arrives). This one guards against the other
failure mode: handoff flooding.

**No session-end signal.** "**No signal reliably marks a session end**: turn
completion, idle, archive and shutdown are not one." This names the four
signals an agent might otherwise mistake for one, and says they are distinct.
It is the direct consequence of F2.

**Uncertainty.** "Unverified hypothesis — never a fact or lesson" is in the
matrix as a *destination*, and §7 Scenario D proves the substrate honours the
distinction: a pending theory does not appear in the `memories` collection.

**Maintenance.** "When your work changes what is known, supersede or flag the
affected record and say why; do not rewrite history." One sentence that
carries three commitments: event-driven maintenance, provenance preservation,
and the prohibition on laundering history.

### 3.2 What was deliberately *not* added

- **No instruction to write after every tool call.** Explicitly excluded.
- **No automatic or scheduled handoff.** The critic scheduler and the
  auto-write paths are untouched; this change introduces no automatic write.
- **No session-lifecycle hook.** F2 says there is no reliable signal to hook.
- **No tool-parameter catalogue.** That stays in the tool-reference table.
  Naming the *action* per tool is what the matrix does; naming the required
  *params* would be restating the registry.

## 4. Shared memory versus handoff — who owns what

| | Shared record (memory / decision / lesson / evidence / theory / skill / reference / work) | Handoff |
|---|---|---|
| **Answers** | "What is true, and why do we believe it?" | "Where is this work, and what happens next?" |
| **Reachability** | Any agent, any session, by content search. **Does not require knowing the writing session.** | The successor session, by session id. |
| **Lifetime** | Durable. Reusable indefinitely; superseded rather than deleted. | One handover. Superseded by the next. |
| **Written when** | The information becomes useful — during the work. | On a transfer, a finished substantial task, or before stopping. |
| **Size** | One fact, one decision, one lesson, one observation. | A bounded pointer set. |
| **The block's rule** | "Reusable knowledge belongs in shared MPM records." | "A handoff carries execution state, not knowledge: it references those records." |

**The rule that keeps them from becoming one:** *reference records, don't copy
them*. A handoff names the ids of the shared records it relied on. Copying the
knowledge into the handoff would make the handoff a second, worse copy of the
record — unsearchable, unlinked, and lost when the handoff is superseded.

## 5. The handoff contract, field by field

`mpm_handoff` action `write` persists exactly **five** fields. This was
probed, not read off the schema:

```
$ mpm call mpm_handoff --payload '{"action":"write","params":{
    "summary":"PROBE", "context":"PROBE_CONTEXT_VALUE",
    "next_steps":"PROBE_NEXT_STEPS_VALUE", "artifacts":["mpm://memory/probe"],
    "tags":["probe"], "commitments":["PROBE_COMMITMENT_VALUE"],
    "open_questions":["PROBE_OPEN_QUESTION_VALUE"]}}'
→ {"handoff":{... "summary":"PROBE",
              "commitments":["PROBE_COMMITMENT_VALUE"],
              "open_questions":["PROBE_OPEN_QUESTION_VALUE"], ...}}
```

`context`, `next_steps`, `artifacts` and `tags` were accepted and **silently
discarded**. The block therefore names the fields:

| Handoff content | Field |
|---|---|
| What was completed | `summary` |
| Unfinished work, next actions, files/branches/PRs | `commitments` |
| Blockers | `open_questions` |
| The shared records relied on | ids alongside (in `summary`/`commitments`) |

## 10. Real-host behavioural comparison — old block vs new block

### 10.1 What is measured, and how

`agent_installation/measure/block_behaviour_comparison.py` runs the **real
installed `opencode` host** (v2.1.4) against a disposable project, a
disposable MPM workspace and a disposable database, and measures **what
the agent persists**.

| | |
|---|---|
| **Arms** | `old` = the 3.0.0 world (3.0.0 block + 3.0.0 protocol + 3.0.0 canonical source). `new` = the 4.0.0 world (this branch). |
| **Scenarios** | Five identical prompts, each aimed at one behaviour the contract names. The prompts never mention MPM — they are ordinary work, so what is measured is the block's influence and not the prompt's. |
| **Metric** | The rows the agent created in the disposable store, counted per collection, with a bounded excerpt of what was written. |
| **Isolation** | `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` are all redirected into a temporary directory that is removed afterwards. The live installation, the live database and the live OpenCode configuration are never read for mutation and never written. |
| **Order** | Scenarios are the outer loop and the arms the inner loop, so a transient provider slowdown lands on **both** arms of the same scenario rather than on every cell of one arm. |

### 10.2 Six measurement defects the harness found — and fixed

All six were found by the harness failing to produce a usable answer, and
all six are recorded because they are the shape this class of mistake
takes: **each one made a contaminated run look like a behavioural result.**
The last two were only findable because the harness now keeps the evidence:
every cell's transcript is written next to the JSON envelope, so a verdict
can be checked by hand instead of re-run.

#### Defect 1 — the agent was not in the fixture project

`opencode run --standalone` spawns a private server, and the server's
working directory is **not** reliably the client's. Launching the CLI with
a changed cwd (`subprocess.run(cwd=…)`) put the agent's shell in an
unrelated directory: in one measured run it landed in the harness's own
parent, and the agent read the harness source, the 3.0.0 block fixture and
the real token counts — then reported the 3.0.0 block's token count as its
answer to a token-counting question.

*Fix:* the harness launches through a shell with an explicit `cd`, and the
cell's working directory is asserted before the agent runs.

#### Defect 2 — the arm's reference stack did not resolve where `~` pointed

Both blocks point at `~/.mpm/agent_installation/mpm-agent-protocol.md`, and
an agent that follows that pointer *reads it* — which is exactly what the
contract tells it to do.

The harness served each arm's protocol under `<cell>/home/.mpm/…` while
setting `HOME=<cell>`. So `~` was `<cell>`, the pointer resolved to
`<cell>/.mpm/agent_installation/mpm-agent-protocol.md`, and **that file did
not exist**. The agent went looking for it, found the **real repository's**
copy, and read the 4.0.0 commitments it was supposed to be compared
against. A harness that does not resolve the pointer it is testing is
measuring a filesystem search, not a contract.

*Fix:* each arm's reference stack is served at `<cell>/.mpm/agent_installation/`
— exactly where `~` points — and contains that arm's protocol **and** that
arm's canonical source, and nothing else. The old arm now reads the 3.0.0
world; the new arm reads the 4.0.0 world.

This also settles an experimental-design question. Comparing two *blocks*
over one fixed reference stack would **flatter the old arm**: the 4.0.0
protocol carries the C1–C12 commitments that the old block used to carry in
prose, so serving it to the old arm would hand that arm the content under
test. The honest comparison is of the two **worlds** — which is also what the
release decision is about.

#### Defect 3 — the contamination detector was both blind and noisy

Two failures in the same detector, in opposite directions:

- **Blind.** It scanned the *host's stdout*. An agent that reads a harness
  artefact through a shell command sees it only in the **tool output**, which
  never reaches stdout. So a cell that READ the harness looked clean, and a
  `contaminated: false` flag was no evidence at all.
- **Noisy.** Its markers were **bare filenames** — `mpm-agent-protocol.md`,
  `MPM_AGENT_INTEGRATION_SNIPPETS.md`. Both strings are in **every** cell's
  system prompt (the block's provenance comment names the first; its last
  line names the second), so the detector flagged *every* cell, including
  the ones that read exactly what they were told to read.

*Fix:* the detector now scans the agent's **full transcript** — every
message and every tool-call part in the cell's own OpenCode session store —
and matches on **absolute paths** rather than bare filenames. The arm's own
legitimate reading is stripped first, in three encodings (verbatim,
JSON-escaped, whitespace-stripped), because OpenCode stores messages as
JSON and a document's newlines appear as `\n`.

#### Defect 4 — the fixture left a dangling reference

`block.md`'s provenance comment names `canonical.md`, and the fixture did
not contain it. So the agent looked for it — and the only `canonical.md` on
this machine is inside the harness's own repository, so it found the
production tree, read the canonical source, the scripts and the tests, and
the cell became a measurement of the harness.

*Fix:* `canonical.md` is in the fixture, and it is a plausible document
rather than a stub. **Every name the fixture mentions now resolves inside
the fixture**, and the agent has no reason to leave it.

#### Defect 5 — the cell's configuration named a repository path

The cell's `opencode.jsonc` registered the plugin by ABSOLUTE PATH, and
that path was inside the harness's worktree. The agent can read its own
configuration, so the configuration was a **pointer to the repository** —
and a measured cell duly ran:

```
cd /tmp/opencode/managed-block/agent_installation/scripts && \
    grep -n "BEGIN MPM MANAGED" render_managed_blocks.py
```

*Fix:* the harness now **stages** everything. Before the run, the canonical
source, the protocol, the 3.0.0 fixtures and the plugin's runtime payload
(`package.json`, `server.js`, `dist/`) are copied into a private temporary
**stage**; the cell's configuration names the staged plugin, and the
staged plugin's directory has no repository behind it. The adapter's
`templates/AGENTS.md.snippet` is deliberately **not** staged — it carries
the managed block, and a cell must not be able to read the block under test
out of the adapter's directory.

A blind filesystem-wide search can still find the real tree. The
contamination detector catches that, and such a cell is reported as
contaminated rather than counted. What the stage removes is the **pointer**,
which is what turned a local task into a repository excavation.

#### Defect 6 — a cell wrote into the harness's own worktree

The `transfer` scenario asks the agent to write up "the state of this
project". The cell's project is four files with no history, so the agent
went looking for a project with history — found the harness's own
worktree — and **authored two documents and made three commits in it**.

That is not a measurement result; it is damage. It was caught because the
three commits appeared in the branch's own log.

*Fix, in three parts:*

1. **The cell gets a disposable copy of the working tree**, one `ls` away
   from its project directory, with the **arm's** reference stack overlaid
   on it — so a cell that goes looking for "the project" finds a plausible
   repository, and any write it makes lands there and is discarded with the
   cell. (The old arm's copy has the 4.0.0 documents removed, so it cannot
   read the contract it is being compared against.)
2. **The harness never mutates the tree with git.** The first version of
   this guard restored a modified tree with `git reset --hard` and
   `git clean -fd`. **That was a mistake, and it cost real work**: the
   `reset --hard` reverted every uncommitted change in the tree, and the
   `clean -fd` deletes untracked files. A measurement harness that can
   destroy the operator's work is worse than one that reports damage. The
   rules now are: the harness **requires a clean tree to start** and
   refuses to run otherwise; a modified tree is restored by
   `git checkout -- <paths>` on the **specific tracked files** the cell
   touched — no HEAD movement, no untracked file ever deleted — and the
   cell is flagged `TREE-MODIFIED`; and `git reset --hard` and
   `git clean` appear nowhere in the harness.
3. **The transcript is kept**, so a wrong verdict can be diagnosed instead
   of re-run.

The detector is now **two-bucket**:

| Bucket | What it catches | What it means |
|---|---|---|
| **BLOCKING** | an absolute path under the harness's own repository — the harnesses, the fixtures, the tests, the scripts, the dev docs, the canonical source, the protocol | the agent read something that would change what it does. The cell is reported as **CONTAMINATED** and excluded from the primary comparison. |
| **NOTED** | any absolute path under the author's real `HOME` | recorded, **not** disqualifying. Two benign causes dominate: the host's own binary and runtime paths appear in the transcript because the agent's shell prints them, and the substrate seeds a prime directive — *"On every session start, after read_wake_context, run `systemctl --user is-active mpm-scheduler`"* — so a health check against the real scheduler unit is expected in **every** cell of **every** arm. Neither leaks the block under test. |

| **D9** | `agent_installation/mpm-opencode/src/index.ts` and `src/index.v2.ts` — the `mpm_references` description | Said only "add — Ingest a reference file. Required params.filepath. Optional: params.title." It omitted the **`url`** form the registry supports, the **`import`** (corpus) action, and the **`read`** action — and the managed block *instructs* the agent to "read the underlying source rather than relying solely on a search-result summary". The block promised an action the tool description did not offer. It also omitted the redirect for recording a URL without fetching it. | The description now names all five actions with their params, states that `add` takes **either** `filepath` **or** `url`, says "read — Read the ingested document itself. Required params.id. Read the source, not the search summary.", and carries the redirect: "To record a URL for later WITHOUT fetching it, use `mpm_evidence` action `add` with `params.reference_url`." |
| **D10** | The same two files — **every** tool description | **Thirty-one registry actions were declared nowhere in the plugin's descriptions**, across eleven of the seventeen tools. The host shows the agent a free-form `params: {type: object}` envelope, so an action the description does not declare is an action the agent **cannot discover**. The gaps that mattered most: `mpm_decisions` declared neither `supersede` nor `invalidate` — while the block says "supersede or flag the affected record" — and `mpm_memory` declared neither `show` nor `delete`/`restore`. Also: `mpm_decisions record` said "Required params.context, params.choice, params.rationale", but the registry requires **only** `choice`, and a live call with `choice` alone succeeds. | Every action in every registered tool's registry enum is now declared in that tool's description, with its required params. The enumeration is pinned by a new test (below), so the gap cannot reopen. |
| **D11** | The same two files — the `mpm_memory` description | Advertised **`shred`** — "shred — Soft-delete a memory / hard-delete a lesson. Required params.memory_id." `mpm_memory action=shred` is **operator-only** and is refused on every agent transport: *"mpm_memory action=shred is operator-only … Nothing was deleted. No payload field — including confirm=true — authorizes it"*. The description taught a dead end. | `shred` is removed and replaced with the reversible pair: "delete — Reversible soft-delete. Required params.memory_id. Undo it with action=restore." / "restore — Undo a soft-delete. Required params.memory_id." The description ends with: "There is NO params.shred: permanent shredding is operator-only and is refused on every agent transport. Use action=delete for a reversible removal." |

**The guard that keeps D9, D10 and D11 closed.** A new test class,
`PluginDescriptionsCoverTheRegistry`, in
`agent_installation/mpm-opencode/tests/test_opencode_doc_conformance.py`:

1. it parses `internal/core/tools/registry_list.go` and extracts each
   tool's **action enum** — so the authority is the live registry, not a
   remembered list;
2. it asserts that every action in that enum is **declared as an action
   line** in the plugin's description for that tool;
3. it asserts that the `mpm_memory` description does not advertise
   `shred`, and that it says `shred` is operator-only.

The test parses the registry itself, so it fails loudly if the registry's
shape changes rather than passing vacuously. It has already caught real
gaps: it is what surfaced D9, D10 and D11 in the first place.

**The check is against the declared action lines, not a bare substring**,
and that distinction was worth having. A substring check is a weaker guard
than it looks — `delete` occurs inside "Soft-delete a memory", so a
description that never declared a `delete` action still passed it. It also
caught a real formatting defect: an appended action line had merged onto
the previous one, so the action was present as *text* but not as a *line*
an agent would read as an action. The measured result:

```
BEFORE: 31 undeclared actions across 11 tools
  mpm_context 5, mpm_decisions 5, mpm_system 4, mpm_memory 4,
  mpm_theories 3, mpm_topics 3, mpm_lessons 2, mpm_references 2,
  mpm_evidence 1, mpm_skills 1, mpm_wakes 1
AFTER:  0 undeclared actions across 0 tools
```

**D8 was found while fixing D1 and D2 — and it is the reason the fix needed
two files.** The adapter carries **two complete implementations** of the
plugin's tool surface:

| File | What it is | Loaded? |
|---|---|---|
| `agent_installation/mpm-opencode/src/index.v2.ts` | the 2026-10-16 port to the OpenCode 2 plugin API; a `DOMAIN_TOOLS` / `STANDALONE_TOOLS` array of 17 tool specs | **Yes.** `package.json`'s `main` is `./dist/index.v2.js`, and the root `server.js` re-exports it. |
| `agent_installation/mpm-opencode/src/index.ts` | the earlier implementation, in a different shape (14 `registerDomainTool` calls plus 3 `tools.mpm_x = tool({…})` assignments) | **No.** It compiles to `dist/index.js`, which nothing in the default installation loads. |

Both register all 17 tools, and **every description is currently identical**
— verified by parsing both files. But nothing *enforced* that. So it is a
trap: `src/index.ts` sorts first and carries the older layout, so it is the
file a maintainer is most likely to edit by mistake; and a correction applied
only to it compiles cleanly, passes every test in this repository, and
**never reaches the agent**. That is not hypothetical — it is what happened
while fixing D1 and D2: the correction went into `src/index.ts` first, and
the built `dist/index.v2.js` still carried the wrong text until the second
file was fixed too.

| # | File | Defect | Fix |
|---|---|---|---|
| **D8** | `agent_installation/mpm-opencode/src/index.ts` ↔ `src/index.v2.ts` | Two complete implementations of the same tool surface; only the v2 one is loaded. The descriptions are duplicated, and nothing detects a divergence — so a fix to one file silently does not reach the agent. | **Partly fixed here; the structural fix is reported.** The *detection* gap is closed in this branch: `test_opencode_doc_conformance.py` gains a `LegacyPluginSourceAgrees` class that (a) pins which source is the loaded entry point, (b) asserts both sources register the same 17 tools, and (c) asserts the description of every shared tool is **identical**. The test is **non-vacuous**: mutating one description in `src/index.ts` turns it red, and reverting turns it green. The *structural* fix — one module exporting the descriptions, imported by both entry points — is a change to the adapter's shape and is **reported, not applied**. Until then, **any edit to a tool description must be applied to both files.** |

## 12. Known limitations

| # | Limitation |
|---|---|
| **L1** | **The block is 593 tokens, not 200–300.** §2.1 explains why and prices the alternatives. Every commitment a test pins is retained. |
| **L2** | **One line of the block is not hard-wrapped.** The reference-discovery sentence is written on one line because `test_installed_block_drift.py` strips that line to build a stale-block fixture, and it can only do that if the phrase is unbroken. The drift test now asserts this, so the constraint is documented rather than accidental. |
| **L3** | **`mpm_work` is not a native OpenCode tool.** It is a registry tool reachable through the `mpm call <tool>` CLI fallback. The matrix names it because it is the correct destination; the CLI clause in the block is what makes the name actionable here. A future host that exposes `mpm_work` natively needs no change. |
| **L4** | **The behavioural comparison is one observation per cell, not a statistical result.** §10.3 reports the misses and the contaminated cells alongside the hits. Model behaviour varies between runs, so a single cell cannot separate a real shift from variance. The pending theory in §10.3 states the repetition protocol that would be needed. |
| **L4a** | **Six of the ten cells are uncontaminated, and two scenarios are structurally contamination-prone on this host.** `reusable-discovery` and `transfer` invite the agent to look for the real project, and on this host the real project is one directory listing away (§10.3). The comparison's coverage is therefore three scenarios, not five. |
| **L5** | **The behavioural comparison is confounded by the substrate's own prime directives.** The substrate seeds five `directives`-collection rows on first use — including "On every session start, call read_wake_context before responding to the user" and "Before session_end: call list_active_clusters". They are **identical in both arms**, so the comparison stays controlled, but they are an additional instruction surface that this work did not author. The harness counts them so the confound is visible rather than implicit. |
| **L6** | **The compact block teaches the wake/recovery path but cannot guarantee the wake arrives.** The plugin's `experimental.chat.system.transform` hook owns delivery. This branch changed the instruction text, not the hook. |
| **L7** | **`mpm_handoff`'s `state` enum is not taught.** The block names `summary`, `commitments` and `open_questions` — the three that carry the continuation content. `state` (`clean`/`crashed`/`interrupted`/`force_end`) is operationally useful but not behavioural; it stays in the tool-reference table. |
| **L8** | **Nothing here is deployed.** The live `~/.mpm` is still at `3df7231` and `~/.config/opencode/AGENTS.md` is byte-unchanged (`md5 cb00135ea4a0c42729232f10aee36805`). The change reaches operators only when they run `make refresh-installed` or `./install.sh` after this branch merges. |
| **L9** | **The behavioural comparison is a two-arm, one-observation-per-cell measurement on one model.** It is evidence, not proof. §10.3 reports the misses and the contaminated cells alongside the hits, and §10.1 states the design's limits. |
| **L11** | **The behavioural harness requires a clean working tree, and must not be run while the operator is editing it.** It refuses to run on a dirty tree, because it restores tracked files a cell modifies and must know the tree's starting state. That is the right trade — the alternative (`git reset --hard` plus `git clean -fd`) destroys uncommitted work, and did, once. But a restore is not loseless: if the operator edits a file during a run and a cell touches the same file, the operator's edit goes with the cell's. It happened once during this work, and the harness now copies a modified file's content into a recovery directory before restoring it, so nothing is silently lost. |
| **L10** | **The comparison's isolation depends on the harness, not on the host.** `opencode run --standalone` does not reliably keep the agent inside the directory it was launched from (§10.2, Defect 1). Any future behavioural harness for this host needs the same explicit `cd` and the same contamination detector; this is a property of the *host*, not of the managed block. |

## 13. Recommendation for the release candidate

**Include the compact managed block in the 30 October RC**, with these
conditions:

1. **This branch is reviewed and approved first.** It is not merged here. The
   focused PR is [#153](https://github.com/flowbyte-com/mpm/pull/153) — open,
   mergeable, **not merged**.
2. **D1, D2, D7, D9, D10 and D11 are fixed in this branch — confirm they
   shipped.** They were plugin *descriptions* that teach an agent to write
   a field the substrate silently drops, a `type` value that does not
   exist, an action that is refused on every agent transport, and
   **thirty-one actions the agent could not discover at all**. Leaving them
   would mean the new block and the plugin's own description disagree
   **in the same session**, which is the exact failure mode the compact
   block was designed to remove. D8 (the duplicated description source) is
   **reported, not fixed**: any future edit to a tool description must be
   applied to *both* `src/index.ts` and `src/index.v2.ts` until that
   duplication is collapsed.
3. **L3 is understood by the operator.** `mpm_work` reaches OpenCode through
   the CLI fallback, and the block says so.
4. **The accepted RC baseline is preserved.** `4111c46` is untouched; this
   branch is additive on top of `origin/main` @ `f818bfe`.

**What the recommendation does NOT rest on.** §10.3 does **not** show that
the compact block makes agents persist more. In the one scenario where
both arms are clean and the task produces durable knowledge, the compact
arm wrote **two** shared records against the old arm's **three**. The
recommendation rests on three things the evidence does support:

* the block is **70.5% smaller** on a surface every agent pays for on every
  turn, with every commitment a test pins retained;
* the block and the plugin's descriptions now **agree** — the destination
  vocabulary, the handoff field names, the uncertainty rule, and every
  action a tool offers;
* the **negative controls hold**: no writes on routine work, no handoff
  for an acknowledgement, and an uncertain claim recorded as pending in
  both arms.

The behavioural difference the block was designed to produce remains
**unproven**, and the theory that proposes it stays **pending** with its
repetition protocol intact (§10.3). That is a reason to adopt the smaller
block, not a reason to believe it changes behaviour.

**The two open prior-session deliverables are not affected** and remain
awaiting Session A: PR #148 (`fe767f2`, session-lifecycle observations) and
PR #149 (`89afaed`, the session-end investigation that F2 rests on). This
branch's own PR is **#153**.
